1.1 CRITICAL POST-MIGRATION NOTE (retained from v46)
After SQLite → SQL Server migration, most numeric/boolean columns were declared NVARCHAR (text) instead of DECIMAL/INT/BIT.

Universal rules:

Numeric NVARCHAR in SQL → CAST(col AS DECIMAL(18,4))

Numeric NVARCHAR in Python → safe_float(value)

Boolean NVARCHAR in SQL → WHERE col = '1'

Boolean NVARCHAR in Python → is_active_true(value)

7. TRANSLATION & CALENDAR SYSTEM (v47 — UPDATED)
7.1 Overview
The system supports dual-language (EN/FA) and dual-calendar (Gregorian/Persian/Hijri) switching across ALL modules.

Fundamental principle:

DateKey is the only storage format. The calendar is a display concern only. DimDate is the only converter.

7.2 Two-Layer Translation System (unchanged)
Layer	What It Translates	Storage	Mechanism
UI	Buttons, headers, menu	t_Translations	get_translation('key')
Data	Product/project/customer names	FieldName + FieldNameLocal	get_localized()
Calendar	Date display	DimDate	format_date()
7.3 Calendar Switching — CORRECTED FLOW (v47)
The language switch is unified into a SINGLE route.

text
User clicks "فارسی" / "English" in sidebar
    │
    ▼
window.location.href = '/switch_language/<lang>'
    │
    ▼
Server: switch_language(lang)
    session['lang']     = lang
    session['calendar'] = 'persian' if lang == 'fa' else 'gregorian'   ← BOTH set together
    return redirect(request.referrer or '/')
    │
    ▼
Page reloads with both session values in sync
    │
    ▼
All subsequent requests use the SAME session state
RULE: There is no separate /api/set-language. There is no separate calendar field in the UI. The calendar is derived from the language. If a future requirement needs "Persian user viewing Gregorian dates", introduce a separate session['calendar_override'] — do not split the switch logic.

Anti-pattern (removed in v47): sidebar calling /api/set-language with a body {language: 'en'} that only sets lang but leaves calendar='persian'. This caused the "English UI showing Persian dates" bug.

7.6 Date Display / Entry Conventions (v47 — NEW)
Storage: every date column is INTEGER named <Something>DateKey (YYYYMMDD, Gregorian-based).

Display in tables (server-side):

html
<td>{{ display_date(row.ExpectedCloseDateKey) }}</td>
display_date() reads session['calendar'] and formats via DimDate.

Display in tables (JS-rendered rows):

javascript
var closeDate = opp.expected_close_date_formatted || '-';
Never slice date_key client-side. Never convert client-side. The server returns the formatted string.

Entry via picker:

In English mode → Flatpickr (Gregorian grid), value = YYYY-MM-DD

In Persian mode → mds.MdsPersianDateTimePicker (Jalali grid), hidden value = YYYY-MM-DD

Both pickers write Gregorian ISO into the input; date-utils.js converts to DateKey on submit.

API request parameters (filters) always send Gregorian ISO or DateKey — never Jalali strings.

7.7 The *_formatted API Convention (v47 — NEW, MANDATORY)
Every API that returns a date key MUST also return a *_formatted twin.

Python (in every module's api.py):

python
from app.core.date_helpers import format_date

# ... inside the row loop:
'expected_close_date_key': row[5],
'expected_close_date_formatted': format_date(row[5]) if row[5] else '',
Naming: <camelCaseOfKey>Formatted — e.g. expected_close_date_key → expected_close_date_formatted; DueDateKey → dueDateFormatted.

Why: server is the single source of truth for calendar display. Client never computes dates.

7.8 date_utils.js Behavior Contract (v47)
static/js/date-utils.js is the only file responsible for picker initialization. Every page inherits it. Do NOT add per-page picker scripts.

On DOM ready:

Reads window.currentCalendar (injected by base.html from session).

Finds every input[type="date"], .date-picker, .date-picker-hidden.

Destroys any existing picker on the element.

Initializes:

Gregorian → flatpickr(el, { dateFormat: 'Y-m-d' })

Persian → new mds.MdsPersianDateTimePicker(visibleSibling, {...})

Exposes:

window.initDatePickers(root) — full pass

window.reinitDatePickers() — called after a modal opens

window.toDateKey(str) / window.fromDateKey(key) — helpers

Persian picker construction (canonical):

javascript
new mds.MdsPersianDateTimePicker(visibleEl, {
    targetTextSelector: '#' + visibleId,
    targetDateSelector: '#' + el.id,     // hidden input receives Gregorian ISO
    isGregorian: false,
    dateFormat: 'yyyy-MM-dd',            // value written to hidden input
    textFormat: 'yyyy/MM/dd',            // Jalali text user sees
    enableTimePicker: false
});
Known global: the library exposes window.mds.MdsPersianDateTimePicker. It does NOT expose window.MdsPersianDateTimePicker — always access via window.mds.

7.9 Modal Re-init Rule (v47 — MANDATORY)
Modals hidden on page load are skipped by the initial pass. Every modal that contains a date input needs ONE line:

javascript
$('#myModalId').on('shown.bs.modal', function () {
    if (typeof window.reinitDatePickers === 'function') {
        window.reinitDatePickers();
    }
});
7.10 Migration Recipe — Apply to Any Page
4 steps. No exceptions.

API — for every *DateKey returned, add *Formatted via format_date().

Template (table) — replace manual date slicing with {{ display_date(row.MyDateKey) }} (Jinja) or item.myDateFormatted (JS).

Template (inputs) — leave <input type="date"> as-is. No extra markup needed.

Modals — add shown.bs.modal re-init (one line per modal).

No other files change. date_utils.js, date_helpers.py, base.html are global and complete.

7.11 Common Pitfalls (v47 — NEW)
Symptom	Cause	Fix
English mode shows Persian dates	/switch_language not setting calendar; or sidebar calls /api/set-language instead	Route must set BOTH lang and calendar; sidebar must call /switch_language/<lang>
Persian mode shows Gregorian picker	window.currentCalendar undefined at init time	Check base.html injects it BEFORE date-utils.js loads
Picker opens but shows Gregorian grid with Persian labels	Flatpickr (not the mds one) is initializing	Confirm mds.bs.datetimepicker.js loaded and window.mds.MdsPersianDateTimePicker exists
Modal date input has no picker	Auto-init ran before modal shown	Add shown.bs.modal handler
Date off by one day	Client-side new Date() timezone drift	Never compute dates client-side
API returns *_formatted: '' even in Persian mode	format_date reads session['calendar'] = gregorian	Verify session after language switch
